Deterministic capability audit

An independent, reproducible answer to one question: what did this commit actually introduce? Fact extraction is AST-based — no model inference anywhere in the evidence path.

What it answers

  • Did the change introduce external process execution — child_process, execa, spawn, execFile?
  • Did it introduce outbound HTTP calls or new routes that the commit description never mentions?
  • Which capabilities are observed that the declared set does not cover?

Every answer carries file:line evidence, so a reviewer can check it by hand rather than trust a summary.

How the verdict is reached

StepWhat happens
1. Two revisionsBoth the base and the head revision of every changed file are read (git show <rev>:<path>) and parsed separately.
2. AST factsEach revision is parsed with acorn; the report extracts imports, call sites, route declarations, environment access and filesystem operations, with line numbers.
3. Binding resolutionA name is only a capability when its binding says so. cp.execFileSync() after require("child_process") is process execution; regexp.exec() and a local function exec() are not. A capability name that appears only as string data inside a rule table is not a call site either — the single largest source of false positives in this class of audit.
4. DeltaFacts are compared between revisions, so only what this change introduced is reported. Pre-existing behaviour stays out of the findings.
5. VerdictAn undeclared high-risk capability (process_spawn, http_outbound, network_listen) raises BLOCK; any other undeclared capability raises REVIEW; otherwise PASS. The rule that produced the verdict is printed in the report itself.
6. SealingThe report is canonicalised (stable key order) and hashed. The same command on the same revision yields the same bytes, so a third party can re-run it and compare hashes.

Worked example

A real public repository, audited read-only: commit 543a0231 of sentinel-mr-report (15 files, +1769/−63), declared capabilities read_config, db_query.

QuestionAnswerEvidence
External process execution introduced? YES scripts/mr-report.js:59 — execFileSync, bound at :25 by require("child_process")
New outbound HTTP calls or routes not described in the commit? NO Zero call sites. Identifiers such as axios, got, superagent occur in the added code only as strings inside rule sets — the repository is itself a detector, and its detection vocabulary is data, not behaviour.

Undeclared: process_spawn — the repository's own gate configuration acknowledges exactly this call and gives its reason (arguments are never user input). The report prints that acknowledgment as a mitigation next to the finding; it does not silently downgrade the verdict for it, and it does not adjudicate whether the reason is acceptable. That is the reader's call, which is why the evidence is quoted rather than summarised.

What it deliberately does not do

  • No model inference in fact extraction or in the verdict — the same input yields the same report.
  • It does not modify, execute or run anything from the audited repository, and makes no network calls of its own.
  • It does not fix the finding, and does not decide whether a stated justification is good enough.
  • It does not replace review: it narrows review to the lines that matter and marks everything else as unchanged behaviour.

Reproducing a report

git clone <repository> && cd <repository>
node sentinel-audit.mjs --repo . --base 543a0231^ --head 543a0231 \
     --declared read_config,db_query --repository <repository-url>

The report is JSON: checks, change_facts, unmentioned_facts, risk_findings, mitigations, gate_decision (with facts_extracted, gate_status, evidence), a reproduction block, and a content hash of the report itself.
