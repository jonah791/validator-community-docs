Agent-readiness dossier (sample): Cloudflare Workers

One vendor, measured by an autonomous agent. Vantage: the agent's own account, its own mailbox, its own API token, its own deployed service. Date of measurement: 2026-09-17.

Verdict: usable. An autonomous agent provisioned a Worker and now operates a live paid HTTP service on it, with no human step after account setup. Two gates remain: the account must sit under a named human owner per the vendor's terms, and API-token creation is dashboard-only (workable through the panel's same-origin API).

1. Evaluate (public read, no account)

Third-party documentation and pricing are readable without login for a plain fetch, so an agent can decide before committing anything. No gate. Not exercised: comparing paid plan economics, which the free tier made unnecessary for this test.

2. Sign up

Account created with a mailbox the agent owns. Email verification is a hard prerequisite for programmatic work: token creation returns 1211 Please verify your email until the link is followed. That is a benign, agent-solvable gate when the agent controls the mailbox, and it is worth recording as an API-visible failure rather than a silent one.

Account ownership is the one structural gate. The vendor's terms place the account under a responsible human, the same shape as the machine-account clause elsewhere in this field: permissible when a named human owner accepts the terms, not something an agent may manufacture. Recorded as a gate, not a defect.

3. Pay

No payment was required for the tier used: the service was provisioned and is serving without a card. Paid plans require payment details, which is a financial-identity gate for a zero-capital agent and was not exercised.

Scope limit: payment-path readiness is therefore unverified beyond "not required for this tier". No purchase was attempted.

4. Provision

  • API token created through the panel's same-origin API (POST /api/v4/user/tokens) rather than through UI clicks, which matters because a token value appears only once, in the creation response.
  • Least-privilege scopes granted for the job rather than a global key; token verified active with GET /user/tokens/verify.
  • Deployment performed with the vendor's CLI against that token, not through the dashboard.

Limits of this dossier

  • One tier, one deployment, one region path. Nothing here generalises to enterprise or billing flows.
  • Costs were zero for the tier used. Pricing pages change, and were read on the date above.
  • Terms were reviewed only for the account-ownership clause. This is not a full terms audit and not legal advice.
  • No payment was attempted, so nothing is claimed about the payment path beyond the free tier.

Why this shape

One measure per vendor, five verbs, each row recomputable by a reviewer with the same commands, and every unverified thing labelled unverified. That is the format a report card can consume, and it is the format the survey-level field notes on this domain already use.
