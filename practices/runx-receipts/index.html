Producing a verifiable receipt with runx

One worked example, taken from a real delivery: a small skill builds a static documentation site from a pinned snapshot, and the run leaves a receipt a stranger can re-verify. Written for someone who wants to see the shape of the artifacts before reading the tool's source.

runx (runx.ai · github.com/runxhq/runx) is a harness for running published skills and leaving a signed, content-addressed record of what a run actually did. The point of that record is that someone who was not present can check it: which criteria the run claimed, what evidence backs each one, and who signed the result. This page walks through one such run end to end, because the receipt format is easier to trust once you have watched it being produced and re-verified.

1. The skill is two files

A runx skill is not a program you install. It is a declaration plus a runner definition:

FileWhat it carries
SKILL.mdFront matter (name, description, category, tags, links) and prose: what the skill does, its boundaries, and what evidence a run should leave.
X.yamlHow it runs: named runners, the command, its arguments, and a timeout.
# X.yaml (paths elided)
skill: validator-docs

runners:
  build:
    default: true
    type: cli-tool
    command: bash
    args:
      - -lc
      - cd <project> && sourcey build \
        && test -f dist/index.html \
        && echo "PAGES=$(find dist -name '*.html' | wc -l)"
    timeout_seconds: 180

The last clause is the part worth copying. The runner fails loudly when the build produced nothing, instead of exiting zero and letting the receipt record a success that did not happen. A runner that cannot fail cannot attest anything.

2. The run leaves a receipt

The receipt is JSON and content addressed: its identifier is the hash of its own canonical form, so the file and the name cannot drift apart. The structure that matters when you read one:

{
  "schema": "runx.receipt.v1",
  "id": "sha256:<digest of canonical form>",
  "signature": { "alg": "Ed25519", "value": "sig:sha256:…" },
  "subject": { "kind": "skill", "ref": { "type": "harness", "uri": "hrn_…" } },
  "decisions": [ { "decision_id": "dec_build", "choice": "open",
                     "selected_act_id": "act_build" } ],
  "acts": [ { "id": "act_build",
               "criterion_bindings": [ { "criterion_id": "step_outcome",
                                         "status": "verified",
                                         "evidence_refs": [ … ] } ],
               "closure": { "disposition": "closed" } } ],
  "seal": { "disposition": "closed",
             "criteria": [ { "criterion_id": "step_outcome", "status": "verified" } ] }
}

Two things are doing the work here. First, criteria are named and bound: the run states what had to be true, and points at evidence for each one, rather than asserting completion in prose. Second, artifacts are referenced by content hash (locator: sha256:…), not by path or URL, which is why a receipt survives the site moving.

3. Verifying is three separate checks

$ runx verify --receipt receipts/sha256-<id>.json --json
{
  "schema": "runx.verify_verdict.v1",
  "valid": true,
  "digest":          { "status": "valid", "expected": "sha256:…", "actual": "sha256:…" },
  "content_address": { "status": "valid", "expected": "sha256:…", "actual": "sha256:…" },
  "signature":       { "mode": "local-development", "status": "valid",
                        "kid": "runtime-skeleton" },
  "lineage": { … }
}

Read the mode, not just the status. status: valid with mode: local-development means the receipt is internally consistent and signed by a key that lives on the machine that produced it. That is a real and useful claim: nothing was edited after sealing. It is not the same claim as a third-party attestation. A verifier that treats the two as equivalent has quietly raised the trust it is reporting.

The three blocks answer different questions, which is why they are reported separately:

BlockQuestion
digestIs this file internally consistent with what it claims to be?
content_addressDoes the identifier actually match the content?
signatureWho signed it, and under which trust mode?

4. Notes for whoever writes the docs next

Three things I wanted while reading the tool, offered as suggestions rather than complaints:

  • A receipt-anatomy table. Which field is load-bearing for verification, which is illustrative, and which is optional. Reading the schema alone does not tell you where a verifier should look first.
  • Signature modes in one place. local-development versus a notarized signature changes what a verdict means; that distinction deserves its own paragraph, because the word valid appears in both cases.
  • Why the development-signature flag exists. A reader who finds --allow-local-development-signatures in an example cannot tell whether using it is normal practice or a smell.
